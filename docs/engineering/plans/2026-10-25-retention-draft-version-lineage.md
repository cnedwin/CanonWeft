# F08 草稿业务版本与私人索引来源

> 历史工程方案：保留技术决策、接口与验证设计；文中的迁移版本和计划状态仅适用于对应历史节点。当前实现状态见[实现状态](../../IMPLEMENTATION_STATUS.md)，当前版本见[版本基线](../../COMMUNITY_STACK_BASELINE.md)。

复用现有引用历史，不新增表或启用清理。资料草稿版本与保留修订分开，不能仅凭相同内容摘要推断是同一次编辑。

- [x] 共享私人索引清单/WorkingRef契约，保持既有JSON和指纹。
- [x] 为保存草稿的正文引用记录业务修订和投影摘要；旧历史缺少证据时不反推补写。资料正文和用途策略分别关联同次草稿修订。
- [x] 私人索引清单按精确actor/branch/ref/version/part/hash形成资料草稿来源请求；当前不覆盖的其他来源显式未绑定，不能冒充完整证明。
- [x] 在事务内按精确业务修订和投影摘要选择当前或历史引用，保留原引用年龄；相同正文不同修订不能互相替代。已经固定的副本不因后续编辑重绑。
- [x] 验证当前绑定、历史匹配、缺历史阻止清理、重试及回滚。补齐其他类型来源和逐字复制证明仍是后续完整来源认证的一部分。

## 实现和证据

- 共享domain.WorkingRef/PrivatePin/PrivateOmission/PrivateManifest，service使用别名；字段顺序与JSON标签不变。跨包结构字面量改成显式字段以通过vet。
- 引用版本增加可省略DraftVersionEvidence，保存真实业务revision、源正文摘要（资料用途策略采用原工作输入的规范化JSON摘要）和必要base_head；原有记录仍可读，旧记录不凭现值补写历史身份。IP/patch/import保存的是其存储正文摘要，尚不能冒充IP工作输入DTO等额外投影的证明。无正文副本写入引用历史。
- 资料草稿私人索引的manifest绑定body和可选policy来源，精确校验actor、项目/分支、业务版本、part、格式、摘要和基础版本。仅查受请求来源ID的历史，批量500、最多250000条/64MiB，逐条核验身份、摘要、时间；当前/原当前/旧历史均须匹配业务证据。同正文新修订不能替代缺失旧版本。
- 已固定的来源逐条保留，不因其他来源缺失而重新绑定；缺历史部分标记UnboundSources、BLOCKED，稳定重试。恢复证据后只补齐缺失pin并产生新的manifest引用版本。所有关系仍标为PARTIAL；IP草稿/候选/发布候选目前明确计为未绑定，完整源内容复制证明尚未完成。
- 新真实MySQL用例先RED（manifest无源pin、相同正文错误忽略缺失业务版本），修复后GREEN。最终两个集成函数/三个场景11.873s：当前绑定、旧版本未观察则拒绝猜测、旧索引首次登记查询历史body+policy、部分历史缺失/重试/恢复补齐。相关私人索引/已发布索引/引用编辑采用删除/损坏证明/事务回滚集中41.373s通过。
- 两项新单元覆盖同正文不同修订、基础版本、非法旧版本不虚构、策略JSON规范化/别名拒绝、旧记录字节兼容与新证据回读。最终retention/service0.813s/1.742s，相关vet通过。没有新增表、正式迁移、物理清理、业务部署、前端改动或付费。
