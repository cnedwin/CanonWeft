沿用完整底座计划。复用已有引用版本中的sources，不新增第二套关系权威或启用正式清理。

- [x] 对实际working/knowledge chunks的私密副本登记固定所属index manifest依赖；回执output引用登记同call output依赖。来源存在、项目归属和摘要必须匹配，不能按任意hash猜源。
- [x] 同事务预计算引用版本，源先于副本固定其精确revision/hash；副本内容未变时保持原来源pin，不随源编辑或采用自动重绑。历史加载只取被引用版本，批量、有界、验证身份/摘要/时间，缺少历史拒绝写入。
- [x] 期限图按(ID,revision)解析历史节点；旧候选后来采用不会改写旧副本的期限，历史节点自身不成为待删除的当前对象。规范化历史输入参与计划hash。
- [x] 明确PARTIAL是已登记的直接关系，不声称全部来源已穷尽。index manifest内部来源、上下文和运行输入仍需完整处理；所有执行门禁继续关闭。
- [x] 定向单元及真实MySQL验证初次绑定、生命周期变化后保留旧pin、重试稳定、缺失/损坏历史拒绝和多层期限，更新证据。

本节点不把索引归属FK冒充完整内容溯源。声明式目录仅用于登记已知直接依赖；后续完整内容来源认证须逐项补齐后才能将Inventory.Complete设为true。

## 实现与验证

- 实际登记器先以有向图预分配本次修订，再在一个事务内写入来源、引用和不可变版本。已固定且内容未变的副本保持原pin；新增依赖使用实际父引用的本次修订。无法找到确切原输出的迟到取消回执报告UnboundSources并置BLOCKED，不捏造call输出版本，也不变更结算。
- 历史加载按精确(id,revision)分批500，只读取被引用闭包；项目、主键、摘要、时间和父版本早于子记录均核验。最多250000节点/1000000边，历史正文无复制，历史记录总64MiB；单条引用记录允许1MiB容纳既定4096pin上限，财务原始payload仍限64KiB。当前引用和历史证据分别存在，不把历史版本当作仍活动的blob引用。
- 期限图接受明确HistoricalReferences并规范化纳入计划hash；缺失、替换、重复、不相关历史及循环拒绝。旧候选采用后的历史期限继承有行为RED→GREEN证据；历史排列稳定和1024来源记录回读专项通过。旧图专项与整个retention/service最终通过0.781s/1.816s；回执blob来源补充断言通过0.562s。
- 两项新真实MySQL9.7.4测试一次6.533s：真实本机嵌入→私人检索索引→来源登记→删除生命周期改版仍固定旧pin→损坏/修复/删除旧历史；合法取消后的迟到成功回执不伪造缺失call输出且不重记费用。三项相关采用/并发/601资源跨批登记组合8.244s；相关vet通过。
- 无新表、正式迁移、清理执行、UI部署或付费调用。index manifest内部各业务版本、context/冻结输入、完整发布索引保留证明和原文过期/恢复仍是下一阶段，不把此PARTIAL关系登记当作F08完成。
