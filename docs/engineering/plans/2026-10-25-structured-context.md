# 长篇结构化上下文实施计划

> 历史工程方案：保留技术决策、接口与验证设计；文中的迁移版本和计划状态仅适用于对应历史节点。当前实现状态见[实现状态](../../IMPLEMENTATION_STATUS.md)，当前版本见[版本基线](../../COMMUNITY_STACK_BASELINE.md)。

依据：统一记忆架构、F09-C续接台账及长篇角色/关系复杂度。继续既有分支，不改版本、不改费用授权、不替作者采用作品。

当前问题：RAG虽限制文本片段，但Facts/Hidden/Entities仍整库进入每次上下文；KnownFacts的历史替代检查为平方复杂度。小说越长，越容易在没有必要的情况下耗尽容量。

设计：在同一不可变IP版本内，先做时间和知情过滤，再选择结构化设定。锁定项、显式指定的必需命题/实体、全部世界规则及其条件依据是硬约束；引用实体、能力关联与前提递归闭包完整保留。其余命题按任务焦点、人物/别名、当前状态排序，在预算内完整取舍，不裁剪句子；报告遗漏数量，不能把未取用解释为不存在。NPC只在已知事实集合内选择，不返回秘密或秘密计数。必需项超过总容量继续报错，不用缩减硬约束掩盖。

Ruling：沿用世界规则全部保留的既有契约，不在该历史节点引入规则裁剪。可选结构化材料先保留约三分之一容量，若与必要记忆/完整来源争用则退回仅硬约束重编译；此回退必须留下遗漏统计。旧已存上下文不改写，新增字段omitempty保持旧哈希兼容。

- [x] domain：线性KnownFacts、纯结构选择器与引用闭包；长篇、秘密、关系、能力、必需项定向测试。
- [x] service：接入SearchInput/ContextPackage、RAG编译和容量回退；持久化仍复用context_packages。
- [x] Vue：按已发布设定选择焦点及必需命题，展示取用/遗漏，不让迟到结果覆盖当前条件。
- [x] MySQL真实集成、定向前端检查和一次节点构建；更新证据与续接。
